# 🏀 Contoso Sports — a WebMCP playground wearing a webshop costume

Let's be honest about what this is. The **actual point** of this repo is to poke at
**WebMCP** — the proposed `navigator.modelContext` API that lets a web page hand its
own capabilities to an agent — and see how it feels to build with. You need *something*
for the agent to do, though, and "TODO app #40,000" felt bleak. A sports webshop, on the
other hand, has a catalog, a cart, sign-in, checkout, a profile, order emails… lots of
real surface for tools to grab onto. So: webshop. Sorry, "Contoso Sports."

There is no backend. No real auth, no real payments, no real emails leaving your machine.
The catalog, users, cart, and profiles are static dummy data in `src/data/` plus a bit of
`localStorage`. If you buy a downhill helmet here, you will not receive a downhill helmet.
Manage your expectations accordingly.

## 💡 What is WebMCP?

Normally an AI agent that wants to use a website has to *look* at it: scrape the DOM, guess which
button is "Add to cart", and hope the layout doesn't change. **WebMCP** flips that. The page
publishes a list of **tools** — named functions with a description and a JSON Schema for their
inputs — and the agent simply calls them.

```js
// Without WebMCP: find the button, click it, hope.
document.querySelector('.product-card button.add')?.click()

// With WebMCP: ask the page what it can do, then call it.
navigator.modelContext.listTools()                       // → [{ name, description, inputSchema }, …]
await navigator.modelContext.callTool('shop_add_to_cart', { productId: 'run-001' })
```

The site stays in control: it decides which capabilities to expose, validates the input, and
runs them against the same state the UI uses.

> **Status:** WebMCP is an *experimental proposal* (see the
> [WebMCP spec repo](https://github.com/webmachinelearning/webmcp)), not a shipped standard.
> Browsers don't provide `navigator.modelContext` natively yet, so this repo ships a small
> hand-written stand-in (`src/webmcp/runtime.js`) that installs the same-shaped API on the page.
> The API surface may change as the proposal evolves.

## 🧩 Add your own tool

A tool is `{ name, description, inputSchema, execute(args) }`. `execute` returns an MCP-style
result. The shop's tools live in `src/webmcp/tools.js` and are registered on mount by
`WebMCPProvider.jsx`; you can also register one from the console to experiment:

```js
const unregister = navigator.modelContext.registerTool({
  name: 'shop_say_hello',
  description: 'Greet the shopper by name.',
  inputSchema: {
    type: 'object',
    properties: { name: { type: 'string' } },
    required: ['name'],
  },
  async execute({ name }) {
    return { content: [{ type: 'text', text: `Hello, ${name}!` }], structuredContent: { name } }
  },
})

await webmcp.callTool('shop_say_hello', { name: 'Ada' })
unregister()
```

Tools that change app state should mutate the stores in `src/lib/` (not React state) — see the
note on external stores at the bottom. Every call, including your custom tools, is audited
automatically.

## 🎯 The actual point: WebMCP — agent tools

The app exposes its capabilities to an in-browser agent via a **WebMCP** layer, following
the shape of the proposed `navigator.modelContext` API. Tools register themselves on the
page and operate on the **same state the UI uses**, so when an agent does something, the
interface just… updates. Cart badge ticks up, pages navigate, etc. No mirror world, no
duplicated state to drift out of sync.

Two global surfaces get installed on the page:

- `window.navigator.modelContext` — `registerTool`, `listTools()`, `callTool(name, args)`
- `window.webmcp` — a friendlier wrapper: `listTools()`, `callTool(name, args)`, `subscribe(fn)`

### 🧰 Available tools

| Tool | Purpose |
| --- | --- |
| `shop_search_products` | Search/filter/sort the catalog — details below |
| `shop_get_product` | Full record for one product by id or SKU (specs, features, sizes, colourways…) |
| `shop_list_facets` | Valid categories, brands, tags, price range and sort options |
| `shop_add_to_cart` | Add a product by `productId` or SKU (+ optional `quantity`) |
| `shop_view_cart` | Cart lines plus subtotal/shipping/tax/total |
| `shop_update_cart_item` | Set an item's quantity (0 removes it) |
| `shop_remove_from_cart` | Remove an item |
| `shop_sign_in` | Sign in with a demo account (required before checkout) |
| `shop_get_auth_status` | Report whether a user is signed in |
| `shop_get_user_profile` | The signed-in user's facts: contact, membership, loyalty, saved address, preferences, order stats |
| `shop_update_shipping_address` | Update the saved shipping address (partial updates supported) |
| `shop_checkout` | Place the order (requires sign-in + non-empty cart) |

Every tool returns an MCP-style result: `{ content: [{ type: 'text', text }], structuredContent }`.
Handled errors come back as the same shape with `isError: true` instead of throwing — agents
hate surprises.

#### 🔎 Product search

`shop_search_products` free-text `query` matches **all** whitespace-separated terms (in any
order) across name, brand, category, SKU, description, details, features, specs, colourways
and tags — so `"downhill mtb helmet"` finds the DH helmet without you spelling it out. Mix
it with filters:

| Param | Meaning |
| --- | --- |
| `query` | Free text (all terms must match) |
| `category` | One of the catalog categories, or `All` |
| `brand` | Exact brand, e.g. `Contoso` |
| `minPrice` / `maxPrice` | Price range |
| `minRating` | Minimum rating (0–5) |
| `inStockOnly` | Exclude out-of-stock |
| `onSaleOnly` | Only items where `listPrice > price` |
| `tags` | Require all tags, e.g. `["downhill","helmet"]` |
| `sort` | `featured`, `price-asc`, `price-desc`, `rating`, `newest`, `reviews` |
| `limit` | Max results (default 10) |

```js
await window.webmcp.callTool('shop_list_facets', {})                       // discover valid values
await window.webmcp.callTool('shop_search_products', { query: 'downhill mtb helmet' })
await window.webmcp.callTool('shop_search_products', { category: 'Cycling', onSaleOnly: true, sort: 'price-desc' })
await window.webmcp.callTool('shop_get_product', { productId: 'CS-CYC-003' })  // full specs
```

#### 👤 User profile

`shop_get_user_profile` returns the signed-in user's facts (the password is never handed out —
we're fake, not reckless). `shop_update_shipping_address` takes a **partial** address — omitted
fields keep their current value — and the saved address prefills the checkout form and fills in
anything `shop_checkout` isn't given:

```js
await window.webmcp.callTool('shop_get_user_profile', {})
await window.webmcp.callTool('shop_update_shipping_address', { city: 'Denver', zip: '80202' })
await window.webmcp.callTool('shop_checkout', {})   // ships to the saved address
```

Profile edits persist per user under `contoso.profiles`, so they survive sign-out. The profile
page and the tools share one store, so an edit from either side shows up on the other
immediately.

### 📋 Audit logging

Every WebMCP tool call gets recorded to a persistent, client-side **audit log**
(`src/lib/auditLog.js`), because if an agent is going to run around your webshop you probably
want a receipt. No backend, so it's a capped ring buffer (500 entries) in `localStorage` that
survives reloads. Instrumentation lives in the runtime's `callTool`, so *every* call is captured
regardless of who made it.

- **`tool_call`** entries record: timestamp, session id, tool name, redacted args, `ok`/`error`
  status, duration (ms), and a result summary.
- **`checkout`** entries additionally record each completed order: order id, user, item count,
  total, and card last-4 — with `source: "webmcp"` (agent) or `source: "ui"` (checkout form),
  so both paths are audited.
- **Sensitive values are redacted** before storage: passwords/CVC become `••••`, card numbers
  shrink to `•••• 1234`. We're demo-grade, not careless.

Inspect or export the trail from the console:

```js
window.webmcp.getAuditLog()      // array of audit entries
window.webmcp.exportAuditLog()   // pretty-printed JSON string
window.webmcp.clearAuditLog()    // wipe the trail
```

## 📧 Email service (order confirmation)

After a successful checkout — from **either** the checkout form or the WebMCP `shop_checkout`
tool — an order confirmation email is composed and "sent" to the signed-in user.

> **No real email is delivered.** The demo users' addresses aren't real inboxes, and real
> delivery would need a mail provider, an API key, and a backend — none of which live here.
> Instead the service builds the actual message and hands it to demo transports.

**Transports** (`src/lib/email/transports.js`) — a transport is `{ name, async send(message) }`:

| Transport | What it does |
| --- | --- |
| `mailbox` | Stores the message in an in-app mailbox so it can be previewed in the UI |
| `dev-file` | Writes a real `.eml` file to `sent-emails/` in the repo root (dev only) |
| `console` | Logs the message (available, not on by default) |

The `.eml` files are proper RFC-822 `multipart/alternative` messages (text + HTML), so you can
double-click one and it opens in a normal mail client — the fake email is at least a
*well-formed* fake email.

**Where you see it**
- `sent-emails/*.eml` on disk (git-ignored runtime data).
- The audit log records an `email` entry per send (recipient, subject, message id, order id,
  and per-transport results).

**Sending real email.** Add a transport that calls your provider (SendGrid/SES/SMTP) and
register it:

```js
import { setTransports } from './lib/email/emailService.js'
setTransports([myProviderTransport])
```

That transport needs a server/API key to hold the credential — which is exactly why it's
intentionally not shipped in a static frontend.

```
src/lib/email/
  templates.js     renderOrderConfirmation(order, user) -> { subject, text, html }
  emailService.js  composes, dispatches through transports, writes the audit entry
  transports.js    mailbox / dev-file / console transports (plug a real one in here)
  mailboxStore.js  in-app mailbox for previewing sent messages
```

## 🗂️ Project structure

```
src/
  components/     Navbar, ProductCard, and the various form/detail bits
  context/        AuthContext, CartContext  (subscribe to the stores below)
  data/           products.js, users.js  (static dummy data)
  lib/            cartStore, authStore  (external state shared with WebMCP)
                  pricing, search, orders  (shared logic)
                  auditLog        (persistent WebMCP tool-usage audit trail)
                  checkout.js     (post-checkout effects: audit + send email)
                  email/          (demo email service, see above)
  pages/          Catalog, ProductDetail, Login, Profile, CartPage, Checkout,
                  OrderConfirmation, Tutorial (the in-app /tutorial walkthrough)
  webmcp/         runtime.js      (navigator.modelContext registry)
                  tools.js        (the shop's WebMCP tool definitions)
                  toolHelpers.js  (ok()/fail() result builders)
                  WebMCPProvider  (registers tools; wires checkout navigation)
  styles/         index.css
  App.jsx         routes + protected routes
  main.jsx        app bootstrap
```

> **Why external stores?** The cart and auth live in plain observable stores
> (`src/lib/cartStore.js`, `src/lib/authStore.js`) that React subscribes to via
> `useSyncExternalStore`. This gives the WebMCP tools a synchronous source of truth, so an
> agent's sequential calls (add-to-cart then view-cart) always observe fresh, consistent state
> while the UI still re-renders. It's the one genuinely load-bearing design decision in here.

> This is a demo. No real orders are placed and no data leaves your browser. Go wild.
